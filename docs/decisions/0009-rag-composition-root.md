# 0009 · One composition root for the RAG service, with injected providers

**Status:** Accepted · **Date:** 2026-10-30

## Context
`rag/` started as a copy of RagLab. Its modules built their own dependencies: a global `EMBEDDINGS` created at import, a `get_vector_store` behind `lru_cache`, and entry points (server, chat, ingestion CLI) that each picked Chroma on their own. Tests could not swap the vector store or the embedding model without Chroma and Ollama running, ingestion and search shared the embedding model only by accident, and nothing stopped a search from comparing vectors of different sizes. The planned cloud work ([architecture](../architecture.md#planned-cloud-ready-dependency-composition)) needs providers to be replaceable.

## Decision
Each process has one composition root: [`rag/assistant/composition.py`](../../rag/assistant/composition.py). It is the only place that chooses concrete backends (`build_vector_store_provider`, `build_embeddings_provider`, `build_rag_service`). The server, the chat and the ingestion CLI get their dependencies from it; the modules below receive them as arguments.

- **Contracts, not classes:** `VectorStore`, `EmbeddingProvider`, `TextGenerator` (the chat model: `generate` and `stream`, with the model name, temperature, seed and token limit given per call) and `ChunkSource` (the chunk texts of a strategy and the version of that set) are `typing.Protocol`s with only the operations the RAG uses. Their implementations travel together in `RagDeps` (a frozen dataclass: `vector_store_provider`, `embeddings`, `generator`, `lexical`, `clinic`). `RagService(config, deps)` requires every field, `create_app` takes a service or `deps`, and neither it nor the ingestion `main` falls back to Chroma.
- **Lifecycle:** `ChromaVectorStoreProvider` creates one adapter per strategy, reuses it, and offers `invalidate` and `close`. The default provider, the default embeddings and the default generator are one instance per process (`assistant/storage/factory.py`), so ingestion and search use the same embedding model. No `lru_cache` is left in the storage or retrieval layers.
- **Caches follow the index version:** the BM25 index (`LexicalIndex`) and the Chroma adapters are rebuilt when the version of the index changes (the modification time of `manifest.json`, written last by the ingestion). An ingestion run by another process is used on the next question without restarting the server. If `chunks.json` holds a chunk the vector store does not, the search raises `IndexInconsistent` with the reindex command instead of a `KeyError`. The BM25 cache also depends on the clinic profile: its key is the version of the index and the version of the profile, so a change to the lexicon rebuilds the index. The lexical index and the pipeline get the same profile instance (`default_clinic_profile()`).
- **Index safety:** the manifest records the embedding model and, when known, the vector dimensions. A query whose vector has another size than the stored ones raises `EmbeddingMismatch` with the reindex command, and the HTTP service answers 503 with that message.
- **Functions stay functions:** `retrieve(question, config, deps)`, `answer(question, config, history, deps)` and `stream_answer(question, config, deps)` take the one `deps` object; the helpers below them take only the piece they use. Pure logic (RRF, tokenizing, prompts) has no dependencies. Callers never pass `deps`: they use `RagService`, which holds it.

The evaluation bench builds its services through the composition root too (`build_rag_service(config)`), so no legacy wrapper that resolves defaults remains. The one leftover is `ChromaVectorStoreProvider`, which falls back to the process default embeddings when none are injected.
- **Language and a second clinic (Stage 6c):** a language is a package (`config/languages/<language>.yaml`) and a clinic is a file (`config/clinics/<clinic>.yaml`); the clinic names its language. `CLINIC_PATH`, `KNOWLEDGE_PATH`, `INDEX_DIR` and `ANSWER_KEY_PATH` point a process at another clinic; a knowledge file that is not a PDF is read as Markdown. The evaluation reads money, durations and clock times by language (`Locale` in `evaluation/normalize.py`), chosen by the `language` of the answer key. The default embedding model is `embeddinggemma` (from 2026-11-03; before, `nomic-embed-text`): it found 100 of 102 extra Portuguese questions against 89, and 44 of 44 in both languages on the first set. Changing it means reindexing: the manifest records the model, and the index is refused as stale when the model changes (both models make 768 numbers, so the size check alone would not catch it). Brazilian Portuguese exists as a language and as the test clinic Sorriso Pleno; with the same embedding model the search finds 42 of 44 questions against 44 of 44 in English.
- **Clinic profile behind a contract:** what the assistant says (its prompts, the refusal sentence, the labels of the conversation, and the two regular expressions that clean the answer) and what is specific to the clinic (its name, its kind, the example treatment, and the rule about treatments with two prices) come from a `ClinicProfileSource` (`rag/assistant/clinic/profile.py`), the `clinic` field of `RagDeps`. `YamlClinicProfile` (`rag/assistant/clinic/yaml_source.py`) reads `config/clinic.yaml` and the language package `config/languages/<language>.yaml`. It checks both on loading (a missing or empty field, an unknown language, or braces in a clinic value stop the load with a message that says what to fix), and it reloads when the modification time of one of the files changes. The prompt functions receive the `ClinicProfile` as an argument, and the pipeline gets it with `deps.clinic.load()`. The English package holds the texts of the project as they were, and `tests/unit/test_prompt_golden.py` keeps the prompts, the cleaned answers and the tokens equal to the values recorded before the change. The word search reads its stop words and synonyms from the profile too: the language package holds the generic words (`stopwords`, `query_synonyms`), `config/clinic.yaml` holds the specialty words (`query_synonyms`), and `YamlClinicProfile` merges them into a `Lexicon` and refuses a word that is in both files. `tokenize(text, lexicon, expand)` takes the lexicon as an argument, so the words of another clinic change the search without code changes.
- **Knowledge behind a contract (Stage 6b):** the content the assistant answers from reaches the chunker as a `KnowledgeDocument` (name, version, clean text per page, and the sections: a title and its lines) produced by a `KnowledgeSource` (`version()` and `load()`, [`ingestion/source.py`](../../rag/assistant/ingestion/source.py)). The source decides where each section starts, so chunking does not guess titles from the text. Chunking, indexing and the manifest know only the document, so a new format is a new source and nothing below it changes. The brochure is the first source: `PdfBrochureSource` ([`ingestion/pdf_source.py`](../../rag/assistant/ingestion/pdf_source.py)) reads the PDF and holds everything that is about PDFs (the list marker, the page header, the text fixes, the ignored note, and the heuristic that finds the titles, which is written for English). `MarkdownKnowledgeSource` ([`ingestion/markdown_source.py`](../../rag/assistant/ingestion/markdown_source.py)) reads a file where each `## Title` is a section; `data/source/dentalsafe.md` is the brochure in that format and a test keeps its chunks equal to the PDF's. Its version is the hash of the file, the same value the manifest recorded before, so no index had to be rebuilt. The manifest's `source_hash` is the version of the document that was indexed, and the index is stale ("the knowledge source changed") when the configured source reports another version. The source is chosen in the composition root (`build_knowledge_source`, one instance per process) and the ingestion `main` requires it. Not done yet: the choice of source by configuration; the evaluation's answer-key validation still reads the PDF text directly (`evaluation/dataset.py`). A Markdown source has no pages, so the `page` strategy gives one chunk and `split` splits the whole text.

## Alternatives considered
- A DI library (`dependency-injector` and similar): hand-wiring four or five dependencies is shorter and easier to read.
- Keeping the module-level singletons: they hide the lifecycle and block fakes in tests.
- Classes (`Retriever`, `Answerer`) that hold the dependencies: same result with more ceremony; a dependency object plus functions was chosen, and switching later is mechanical because the evaluation bench pins the answers.

## Consequences
- The server, the chat and the CLI are tested with fakes, without Chroma or Ollama; coverage of `rag/` went from 88% to 94%.
- Switching the embedding model means writing a provider and reindexing; the mismatch check refuses a stale index instead of returning wrong results. Choosing a provider by configuration is not built yet.
- The version is a file modification time, which is fine on NTFS and ext4 but too coarse on file systems with 2 s granularity.
- The word search options (`LexicalOptions`, Stage 6a-B2) are chosen per experiment. The assistant's experiment uses the libraries for stop words and stems and no synonyms (measured: same pass rate on dev, two more answers right on holdout); the code defaults stay the old behavior so `lex_base` is the control. `RagConfig` carries them to `LexicalIndex` and to `tokenize`, and the index keeps one BM25 per (strategy, options). The optional libraries (`stopwordsiso`, `PyStemmer`) are imported only when an experiment asks for them. The PyStemmer stemmer is built per call because the library forbids concurrent calls on one instance.
